# 歌曲文件缓存（2026-10-16）

## 行为

- 标准 128k 是现有播放器默认音质；实际流验证成功后，在后台缓存此音源最低可用的 128k / 320k 文件。不为无损播放额外下载大文件，也不做转码。
- 首次播放不等待完整下载；后台队列最多 8 首、单个工作线程。Linux 文件锁阻止多进程同时写缓存；同首并发请求合并。下载独立于当前浏览器连接，切歌或拖动不会保存半首音频。
- 完整文件发布后，下次解析优先命中本机文件，不依赖上游 URL、音源启停或解析容器。当前播放票据后续的拖动请求也可以切换到已完成文件。
- 歌曲文件默认最多 5GiB；系统空闲低于 8GiB 时暂停新增。每文件最多 25MiB、下载预算 120 秒。只缓存首次播放后取得的完整文件，不批量抓取歌曲。
- 文件不按天过期；满额时按最近播放顺序淘汰，正在播放的文件有时长相关的保护窗口，保护中的文件拒绝管理员删除。

## 正确性与隔离

- 从头单独获取完整响应，要求成功状态、合理 Content-Length、实际字节数一致，并用 Mutagen 验证媒体类型和时长。已知时长不匹配、明显试听片段、HTML/JSON、截断和超限均不发布。
- 临时 `.part` 文件不提供播放；验证后原子重命名。SHA256 校验值和大小记录在索引中，文件缺失或大小改变自动视为未命中。
- 同平台 ID 按标题、歌手与音质区分；跨平台共享要求服务端搜索目录中已确认的标题、歌手、版本、时长（误差至多 3 秒）。仅浏览器提交同名元数据不会建立跨平台共享，缺少时长时保持平台隔离。
- 不改变个人歌单与收藏，不公开上游地址、密钥和缓存文件系统路径。缓存管理接口沿用 `require_superadmin`。

## 路径与分段播放

- 索引：`backend/.runtime/music-files.sqlite3`（目录 0700，文件 0600）。搜索目录最多 10000 条。
- 文件：`backend/.music-cache/`（线上 root:www，目录 0750，文件 0640）；目录不纳入 Git、镜像构建或常规代码发布包。
- `MUSIC_FILE_CACHE=1` 默认启用。`MUSIC_CACHE_ACCEL=1` 仅在线上 Nginx 已配置内部文件入口时开启，使用 `X-Accel-Redirect` 和原生 Range/206 分段播放。直接请求 `/_music_cache/` 应返回 404。
- 没有 Nginx 内部入口时（本地开发、默认 Docker），使用支持 Range 的 `FileResponse`。当前依赖的 Starlette 版本应通过分段测试后再部署。
- 浏览器可私有缓存已完成的音频响应 30 天；短时播放票据与实际文件保留时间分离。当前票据过期后重新解析仍可命中文件。
- Docker Compose 额外挂载 `blog-music` 和 `blog-runtime` 持久卷；默认关闭 Nginx 加速环境开关，避免访问未共享的目录。

## 交互与管理

- 歌词和翻译成功获取后，永久保存在服务器 `backend/.runtime/music-lyrics.sqlite3`，全站复用；不随服务重启、内存淘汰或音频缓存淘汰失效。已有内存歌词在下一次成功请求时持久化，不批量下载。
- 只保存带时间轴的有效歌词，空歌词和网络失败不永久保存；平台 ID 与歌曲版本隔离。服务端匹配成功的备用平台歌词也会记住对应关系，后续不重复搜索。浏览器传入的备用歌曲不会建立永久的跨歌曲关联。
- 歌词缓存数据库与私有运行数据一起挂载/备份（Compose 已有 `blog-runtime` 卷），不放在公开静态目录中。磁盘写入故障不阻断音乐播放。

- 进度条拖动时只更新预览，指针松开或键盘操作结束后提交一次跳转。取消拖动、切歌后的旧操作不提交；显示真实已缓冲范围。
- 指针拖动由播放器统一处理，以松手坐标为准；提交时立即同步音频时间和界面状态，不等待下一次 `timeupdate`，避免预览消失后回跳到旧位置。拖动不显示输入框红色外框，键盘操作仍保留可见焦点。
- 拖动预览期间暂停缓冲看门狗，提交后重新计时。跳转本身不算稳定播放进度、不立即触发换源。
- 管理员在“音源管理 → 歌曲文件缓存”查看占用、剩余空间、待处理任务和最近 50 首文件，可删除未受播放保护的缓存；下次播放重新尝试缓存。
- 缓存故障应回退到原取流流程，不把后台缓存失败记为当前播放失败。首次上游播放及浏览器到阿里云/Cloudflare 链路仍可能等待。
- 手机/浏览器上报 `error`、`stalled` 等播放反馈，不删除完整服务器歌曲文件；客户端断网或 WebView 报错不代表文件损坏。刷新播放连接时仍优先命中文件缓存，更新票据有效期重试，不因此重新解析上游。管理员主动删除和既有容量淘汰规则保持不变。

## 移动端缓冲恢复（2026-10-17）

- 已完成文件的播放地址使用服务端签名的稳定、不透明缓存键，绑定文件 ID 与内容校验值。重复解析、连接重试和服务重启后重新解析保持同一地址；文件内容或签名密钥变化时地址随版本变化。仍通过限时播放票据检查文件存在性，不公开内部文件入口。上游网络音频仍使用随机短期票据。
- 浏览器的私有 30 天音频缓存可以复用同一版本地址；实际保留时间仍受浏览器容量、微信内置浏览器策略和用户清理行为影响，首次下载仍取决于网络。
- 缓冲检测持续检查近期播放进展，不再把较早播放过 1 秒误认为一直播放正常。缓存歌曲短暂缓冲先尝试继续当前连接，不清空已有缓冲；持续中断时至多自动重连两次，不删除缓存、不误跳下一首，保留进度并提供手动重试。
- 不再等待可能长时间悬挂的 WebView `play()` Promise 才释放换源锁；用户暂停、系统暂停、切歌和拖动均有独立取消与恢复检查。
- 推荐歌单仅将公开共享内容缓存在浏览器本地，重开页面先展示，后台刷新；合并进行中的读取，短时失败自动退避重试。个人收藏、历史和账号令牌不写入该公共缓存。

## 直接播放已知缓存地址（2026-10-17）

- 浏览器额外记住最多 200 条已确认的完整文件地址；不按时间过期，只接受本站签名文件 URL，按平台 ID、歌名、歌手、专辑和请求音质隔离。不会保存上游临时地址、源站凭据或私人歌单。
- 点击已有地址的歌曲时，立即设置 `audio.src` 并调用播放，不先请求 `/resolve` 或 `HEAD`，歌词读取也不占据启动路径。媒体请求仍取决于手机网络；浏览器已经保存音频数据时可以复用其私有 HTTP 缓存。
- 没有已知地址时正常解析。上游音频播放成功后，在独立、可取消的后台任务中通过 `/api/music/cached` 检查完整文件是否下载完毕；该接口不运行任何音源脚本，结果只影响下次播放，不重启当前音频。
- 公开推荐歌单附带其已完成歌曲的缓存地址，浏览器批量记住；不包含其他用户私人歌单地址。批量检查不刷新未播放歌曲的 LRU 时间。
- 文件签名与版本映射保存在私有 `music-files.sqlite3` 的 `file_tickets` 表中。内存票据过期、淘汰或服务重启后，旧地址可以直接恢复，无须先重新解析。恢复仍校验当前签名密钥、文件版本、存在性及大小；源地址票据仍保持原有短期有效规则。
- 已知地址播放失败后才执行服务器刷新，成功地址覆盖旧记录。服务器的歌曲文件不会因清理失效的浏览器地址记录而删除。

参考：[Nginx internal](https://nginx.org/en/docs/http/ngx_http_core_module.html#internal)、[Mutagen 文件识别](https://mutagen.readthedocs.io/en/latest/api/base.html)。
